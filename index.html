Software engineering

Parstock: from register sales to a purchase order

A restaurant knows what it sold and what it bought, but not what it used or what to order next. Parstock connects the two. It reads the register, reads the supplier's invoices, explodes every sale into ingredients through the recipes, forecasts the next delivery window, and prints the order in cases.

IN

Toast POS API

OAuth2 client I wrote on urllib: cached tokens, early refresh, backoff on 429s, paged fetches.

STORE

Raw pages first

Every API response is saved untouched in toast_raw, then parsed. A parser fix replays history without calling Toast again.

EXPLODE

Sales to ingredients

A recursive walk turns nested modifiers into rows, then recipes turn drinks into pounds, pumps and scoops.

FORECAST

Isolated engine

Runs in a subprocess on a pinned interpreter, so app dependency changes cannot move a forecast.

OUT

Order in cases

Usage × window × cushion, minus stock on hand from the ledger, divided by a case size that passed a physical check.

Inventory as an event ledger

Counts, deliveries, usage and waste are appended, never edited. On-hand stock is replayed from the last count instead of stored.

When the shelf and the screen disagree, every step between them is on record, and one spot count fixes that item.

Tenancy that fails closed

Replaced single-store globals with per-request store resolution. With two stores and no choice made, it refuses rather than guesses.

A wrong guess would put one store's order sheet in front of another. A new location inherits 223 setup rows from its brand.

Idempotent invoice import

Importing the same invoice twice changes nothing. A resend only replaces a stored invoice if it carries more priced lines, inside one transaction.

Suppliers resend invoices once prices settle. A blank copy can never overwrite a priced one.

Credentials encrypted at rest

POS secrets are Fernet-encrypted with an owner-only key file, behind read-only API scopes. Production access needs an explicit flag.

The app can read a restaurant's sales. It can never change them.

Tests that survive new data

218 tests. The ones on real POS data assert invariants, like "an unconfirmed delivery is never treated as zero", instead of frozen totals.

A test pinned to "25 orders" broke the day real data arrived. Invariants keep holding as the data grows.

Price movement from invoices

Flags supplier price changes against a median of the first three deliveries, and stays quiet with fewer than three.

Debugging

The gift box bug

The register sells a bundle called “G2G – 8 Smoothies or Juices.” It has no recipe of its own. Its eight drinks live inside it as modifiers. Getting this right took three attempts.

  1. Dropped. The first version did not recognise drinks hidden inside a bundle, so their ingredients were never counted. It looked like the owner was under-buying blueberry, pineapple and granola.
  2. Double-counted. The fix multiplied each drink by the number of bundles. But Toast had already done that multiplication, so usage landed 13–35% above what the store had actually bought.
  3. Fixed, and proven. I checked every one of the 3,054 modifier lines on multi-quantity items. Each one already carried its parent's quantity. Multiply once, not twice.

No unit test caught either bug. Comparing computed usage against supplier invoices did, because a store cannot use more blueberries than it bought.

Forecasting what a juice bar will use

Daily demand for 56 ingredients, modeled from 85 days of sales (7,017 orders), 562 supplier invoice lines, and a 588-row bill of materials typed up from recipe cards. Every method is scored walk-forward: a prediction for day D only sees data from before D.

The early sales exports showed drink sizes on only 24% of orders, all from the morning. Sizes sell at different prices and total revenue was known, so I reweighted the size mix until it matched revenue across all 5,709 orders.

Machine learning · Cloud

Produce photo classifier on AWS

  • Fine-tuned MobileNetV2 in TensorFlow on 2,492 real-world photos of 33 fruits and vegetables. On 558 held-out photos it is right 86.9% of the time, and the answer is in its top three 95.3% of the time.
  • Found 65 test photos that were copies of training photos and removed them before scoring, so the test number isn't inflated.
  • Exported to TensorFlow Lite at float16: 4.5 MB with no measurable accuracy loss. An int8 version was smaller but cost 1.4 points.
  • Served from AWS Lambda through a public URL, with the model in a private S3 bucket and an IAM role that can only read it. One script deploys, one tears down. About 0.2 s per photo once warm.
  • Weakest on look-alike root vegetables: radish, turnip and sweet potato are right 59–64% of the time.

How I work

Check against the real world

Every serious bug in this project was caught by comparing the model to supplier invoices. A test only checks what you thought to ask.

Refuse rather than guess

An item whose case size fails a physical check gets no order number. An ambiguous store gets no screen. A blank is safer than a confident wrong answer.

Say the limits

Every number on this page came from the code and data. Where a result misses its target, the page says so.
